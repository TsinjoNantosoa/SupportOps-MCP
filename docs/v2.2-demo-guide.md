# V2.2 — guide de démonstration reproductible

Toutes les données sont fictives. Ne lancer ces commandes que dans le dépôt local.

## Démo A — MCP sans OpenAI

```powershell
Copy-Item .env.example .env
.\.venv\Scripts\python.exe -m supportops.cli init --reset
.\.venv\Scripts\python.exe -m supportops.cli demo
.\.venv\Scripts\python.exe -m pytest tests\test_e2e_v21.py -q
```

La sortie doit montrer la découverte de `get_ticket`, `search_knowledge`, `get_procedure`, le ticket `INC-1042`, la procédure `outlook-send-failure.md`, une proposition `PENDING`, puis une décision locale et un audit.

## Démo B — diagnostic OpenAI dans n8n

1. Démarrer les deux MCP HTTP et importer les sept workflows.
2. Configurer manuellement le credential OpenAI et sélectionner un modèle tool-capable disponible.
3. Ouvrir le chat n8n et demander : `Analyse le ticket INC-1042, consulte la procédure Outlook et prépare une note technique.`
4. Vérifier dans l'exécution les appels aux deux MCP, les faits, hypothèses, sources, limitations et le `Proposal ID` éventuel.
5. Vérifier que la proposition reste `PENDING` et que le ticket est inchangé.

Ce parcours est **NON VÉRIFIÉ** dans l'environnement courant faute de credential OpenAI.

## Démo C — human-in-the-loop sûr

```powershell
.\.venv\Scripts\python.exe -m supportops.cli proposals PENDING
.\.venv\Scripts\python.exe -m supportops.cli approve PROP-XXXXXXXXXXXX --yes
.\.venv\Scripts\python.exe -m supportops.cli audit
```

Remplacer l'identifiant par une proposition affichée. La CLI affiche le changement exact, demande une confirmation et applique une transaction. Un rejeu avec la même clé peut rendre le même audit à la même identité, mais un acteur/session différent est refusé.

## Réinitialisation prudente

`init --reset` réinitialise uniquement la base locale configurée par `SUPPORTOPS_DB_PATH`. Vérifier la valeur avant de l'utiliser et ne jamais l'exécuter contre une base de production.
