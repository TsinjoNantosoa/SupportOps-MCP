# V2.2 — intégration n8n

## Workflows

| Fichier | Rôle | État de sécurité |
|---|---|---|
| 01 | Chat, agent, mémoire, deux outils MCP | OpenAI à configurer manuellement |
| 02 | Lecture déterministe d'un ticket | Aucun OpenAI requis |
| 03 | Recherche et lecture d'une procédure | Aucun OpenAI requis |
| 04 | Diagnostic structuré multi-serveur | OpenAI à configurer manuellement |
| 05 | Présentation d'une proposition et revue | Wait = intention de revue uniquement |
| 06 | Décision humaine authentifiée | Approbation distante désactivée par défaut |
| 07 | Classification et persistance d'erreurs | Aucune donnée sensible persistée |

Tous les exports sont inactifs, versionnés pour n8n 2.45.7, sans credentials. Ils ont été importés dans l'instance isolée `http://localhost:5681`. Le validateur local vérifie les versions de nœuds, les endpoints, les timeouts, les connexions et l'absence de secrets.

## Import et réseau

```powershell
docker compose up --build -d
docker compose ps
```

Importer ensuite les sept fichiers depuis `n8n/workflows/`, sans activer immédiatement. Dans un même réseau Docker, conserver les noms `supportops-ticketing`, `supportops-knowledge` et `supportops-approval`. Pour n8n sur l'hôte, remplacer par `http://127.0.0.1:8001/mcp`, `http://127.0.0.1:8002/mcp` et `http://127.0.0.1:8010`. Pour n8n en conteneur et Python sur l'hôte, utiliser `host.docker.internal`.

Créer séparément :

1. credential OpenAI ;
2. credential HTTP de service pour lire les propositions et écrire les erreurs ;
3. credential individuelle d'approbateur pour WF-06 ;
4. authentification Header du webhook WF-06.

Ne jamais fournir `approver` dans le JSON : l'API résout l'acteur depuis le credential individuel.
